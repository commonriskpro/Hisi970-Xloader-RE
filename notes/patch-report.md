## CRC convention for the read frame (resolved here)

The parser computes it inline at `0x2f950..0x2f9c6`:

```
0x2f950  subs r2, r7, #2          ; n = frame_len - 2
0x2f956  ldrb.w sl, [sb, r2]      ; wire crc = frame[n]<<8 | frame[n+1]
0x2f968  mov  lr, ip              ; crc = 0 (init)
0x2f98c  lsr.w r3, fp, #4         ; hi nibble of each payload byte
0x2f996  eor.w lr, r3, lr, lsr #12
0x2f99e  ldrh  r3, [r3, #-0x40]   ; table[VA 0x3e2a4] (16 dwords, CCITT)
0x2f9a4  eor.w lr, r2, r3         ; crc = (crc<<4) ^ table[idx]
0x2f9c6  cmp   sl, lr             ; compare against the frame
```

So the frame CRC is **CRC-16/XMODEM** (poly `0x1021`, init 0, non-reflected),
computed over `bytes[0 .. len-2)` and stored **big-endian**.

`tool-reference/Crc16.cs` (`CrcHqx`) is the **same** function. Its main loop is
non-standard (it indexes the table with `crc>>8` and XORs the data byte into the
result), but its two trailing zero-byte iterations complete it. Verified against
2000 random buffers, 0 mismatches. So there is **one** convention, shared by the
bootrom upload frames and the xloader read frame.

The canned bootrom start frame (`fe 00 ff 01 00000004 00000201 1d0f`) matches
neither (XMODEM and CrcHqx both give `0x47e5` over its body), so it is a handshake
constant accepted independently of the frame CRC, not a CRC-derived frame.

**Live confirmation.** The first live attempt shipped a `crc_hqx` that appended two
*extra* zero bytes on top (`0x39d0` where `0x47e5` was required); the bootrom NAKed
all 137 frames with `0x55`. With the corrected CRC the identical sequence returned
141/141 `0xAA` ACKs and the benign read succeeded.

## Correction to notes/plan.md §2.0

The plan's cave pseudocode loads `[r4,#0x3dd]` and compares it with 3 as if it
were the file type. `0x3dd` is the second byte of the big-endian **size** field;
the file type is at **`0x3db`** (`0x2fa48: ldrb.w r1,[r4,#0x3db]`). The stub
compares `[r4,#0x3db]`, and separately reproduces the overwritten
`ldrb.w r3,[r4,#0x3dd]` before rejoining at `0x2fa5c`.
