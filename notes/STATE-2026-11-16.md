## 1. One paragraph of situation

We have arbitrary code execution inside the Kirin 970 factory bootloader (EL3) and we can make
the service tool load **any** bootloader we want, because its `.ktl` loaders are wrapped with a
key the tool itself carries. AOSP Pie was built from source and flashed to `system_a`. The
bootloader rejects it because the missing oeminfo item `0x82` forces `fb_lock_stat = 0`, which
makes AVB mandatory. We located and patched the AVB verdict so the flow accepts the image, and
with the preboot-mode decisions forced we get an actual boot attempt (orange banner), but every
attempt ends in a reset. The leading hypothesis is the in-RAM kernel handoff (BL31 mailbox),
not AVB.

## 4. Toolchain we now own (rebuildable, no old PC needed)

**Build any image variant** from the pristine factory fastboot:

    python3 build/patch_fastboot_kit.py --variant avb | mode | trace | modetrace | boot

`avb` reproduces sha256 `174F6352EFA18D7FC4E47AC0AA85E43F6360F0DFB85E0D7EA75ADFBB10F814F7`
(the exact image used in the sessions), which is a good self-check.

**Wrap it for the tool** with the key extracted from the tool's own DLL:

    python3 build/wrap_ktl.py --dll "C:\Users\Air_M\Downloads\Kirin-Tool-v2.4.2\Kirin-Tool.dll" \
        --wrap hisi970_fastboot_avb.bin fastboot.ktl

then copy `fastboot.ktl` over `<tool>\loaders\hisi970\fastboot.ktl` (keep `.orig`).
Requires `pip install cryptography`.

The key is a UTF-16 base64 string inside the DLL (four layers, RSA-2048). The same key is
present in every copy of the tool we tested, so a fresh download can still load our images.

## 5. Established facts (with evidence)

- No `boot` partition: `kernel_a` (standard boot image v1, ramdisk_size 0) + `ramdisk_a`
  (`AVB0` at +0x1000) + `dts_a` + `vbmeta_a` (AVB0 SHA256-RSA2048, embedded public key).
- Boot chain: BootROM -> xloader -> UCE -> fastboot image (the whole bootloader, at EL3).
- AVB is enforced because of the oeminfo `0x82` gate:

      huawei_fblock: cannot get oeminfo rdlock type info
      huawei_fblock: hwdog_certify->lock_state.fb_lock_stat = 0
      load_hhee: FB Locked on this device.
      hisi_avb: avb_slot_verify_result_error_invalid_metadata

- Replacing the *kernel* boots (G1); replacing *system* does not, because only system is in
  the slot's AVB descriptor chain.
- Response dispatcher `0x1680AC6C(msg, type)`: 0 = OKAY, 1 = FAIL, anything else = silence.
  A NULL msg crashes the OKAY path (`0x1680AA54` initialises the buffer). Use `"OKAY"` at
  `0x169B7E40`.
- Code cave at `0x168011D0` (1584 zero bytes); scratch cells `0x16801600`.
- Preboot mode table at `0x16B12B30` (stride 0x18): check_boot_mode `0x16806E14`,
  check_image_state `0x168097DC`, check_power_state `0x16808098`, check_smpl_state `0x168073C8`,
  check_unlock_misc_info `0x1680624C`, check_powerkey_misc_info `0x1680662C`,
  check_volumekey_state `0x16805EF8`, check_misc_info `0x16808BF4`.
- AVB status translator is called from `0x168ADC0C` (target `0x168AC2F8`); the load-kernel
  body starts at `0x168AE018`; the boot orchestrator is `0x168AE5CC`.
- `oem check-image` is NOT the AVB check; it keeps saying `fail` even with AVB patched.

| `fastboot reboot` with AVB patched | — | banner, then it resets (RAM lost, flash bootloader re-runs) |

## 7. Leading hypothesis for the remaining blocker

The boot attempt reaches the kernel handoff and dies there. `notes/phase1-boot-path.md` already
flagged this: the only in-place jump found was `br x1` at `0x168AA968`, but the image runs at EL3
and the real handoff is expected through the BL31 mailbox (`0x1FF00030` / `0x209E1008`), where
that analysis had only ~60% confidence.

So the open question is no longer AVB — it is **how to transfer control to the kernel from an
EL3 bootloader that was loaded from RAM**.

## 8. Next experiments, in order

1. **Restore the phone** (see section 2) so the bench is safe again.
2. **Reproducibility**: load `modetrace` twice more. If the banner appears every time it is
   deterministic (a decision), not a race.
3. **Persist the trace across the reset**: write the markers somewhere the bootloader flushes
   (e.g. into the `bootfail_info` record) so we can read them after the reset.
4. **Control experiment**: restore the stock `system_a` and load the same patched chain. If the
   stock system also resets, the handoff is the problem; if it boots, our image is.
5. If the handoff is confirmed as the blocker: study `boot_kernel`/BL31 mailbox semantics with
   the RAM read primitive, and consider letting the *flash* bootloader do the handoff while we
   only patch its AVB verdict — i.e. find a way to influence the flash-resident bootloader,
   which is a different (harder) problem.

## 9. Traps to remember (cost hours today)

1. **A driver on the VCOM device breaks the tool.** On the old PC the phone sat as `USB SER`
   with `CM_PROB_FAILED_INSTALL` (no driver) and the tool worked. On Moon the Huawei COM driver
   was bound and the tool hung at "Initializing". Do not install a driver for `PID_3609`;
   there is no INF for it in any HiSuite anyway.
2. **Three copies of the tool's loaders existed on the old PC.** The one that matters is the
   one the shortcut runs. Verify by unwrapping the file the tool will actually load.
3. **A reset wipes every marker.** Never try to read RAM after a reset; use the `rrecord`
   partition (bootloader log) or a persistent cell instead.
4. **`fastboot fetch` is broken** on this firmware (`couldn't parse max-fetch-size '0.5'`).
   Reads: `oem memupload <addr> <len> <file>`; partitions: the tool's dump.
5. **A fresh tool download can fix a hang** that a reboot does not; and killing the tool or
   HiSuite mid-flight leaves nothing permanently broken.
